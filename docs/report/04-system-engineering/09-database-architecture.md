# 4.9 Database Architecture

## 4.9.1 Database role

PostgreSQL is the durable persistence layer for OCR. The database architecture reflects the longitudinal nature of the clinical model and the operational relationship between patients, appointments, and visits.

The database is not designed as a single large patient document. Instead, the system separates stable patient identity from time-dependent clinical and scheduling records.

## 4.9.2 Core relational structure

The central relationship can be summarized as:

```text
Patient
 ├──< Appointment
 └──< ClinicalVisit
          ├── VitalSigns
          ├── Diagnoses
          └── ClinicalNotes

Appointment
 └──< AppointmentEvent

System activity
 └──< AuditEvent
```

This structure preserves the distinction between an appointment and the clinical record generated by an attendance.

## 4.9.3 Patient identity

A Patient represents the continuing identity of the person within OCR. Registration creates the patient record and assigns an MRN.

The patient record contains lifecycle information, including Active, Inactive, and Deceased status. Deceased status is not equivalent to deletion. Historical appointments and clinical visits remain part of the record.

This distinction is important for both clinical continuity and data integrity.

## 4.9.4 Appointment persistence

Appointments represent scheduled or operational encounters with the facility. Their state changes over time.

The project records meaningful appointment changes through AppointmentEvent history. This provides a history of workflow changes without treating every change as a replacement of the appointment itself.

The appointment model therefore contains both current state and event history.

## 4.9.5 ClinicalVisit persistence

A ClinicalVisit represents a facility attendance/clinical record within the simplified OCR model.

A patient can have multiple ClinicalVisit records. This is the core mechanism that protects longitudinal history.

The visit may contain:

- vital signs;
- diagnoses;
- clinical notes;
- status information;
- linkage to an appointment where applicable.

A final visit is not simply overwritten by a later attendance. A new visit is created for new clinical content.

## 4.9.6 Cardinality

| Relationship | Cardinality | Meaning |
|---|---|---|
| Patient → Appointment | 1 : many | A patient may have many appointments |
| Patient → ClinicalVisit | 1 : many | A patient may have many visits |
| ClinicalVisit → VitalSigns | 1 : 0..1 | A visit may have one vital-sign record |
| ClinicalVisit → Diagnosis | 1 : many | A visit may contain multiple diagnoses |
| ClinicalVisit → ClinicalNote | 1 : many | A visit may contain multiple notes |
| Appointment → AppointmentEvent | 1 : many | An appointment may have multiple meaningful events |

## 4.9.7 Schema evolution

The project uses EF Core migrations under the backend project as the authoritative schema-evolution mechanism.

This is important because a database design is not finished when the first schema is created. As requirements and implementation details change, migrations provide a history of structural changes.

The repository also contains a reference SQL document. Project documentation explicitly warns that this reference SQL may lag behind the latest migrations, so migrations are preferred as the source of truth.

## 4.9.8 Transactional integrity

Some operations affect multiple related records and therefore require coordinated persistence.

Check-in is a representative example because appointment state and clinical-visit creation are logically connected. Finalization can also involve a clinical visit and the linked appointment.

The engineering concern is to maintain appropriate transactional integrity: either related changes are persisted consistently, or the operation fails without leaving an unintended partial state.

## 4.9.9 Concurrency limitations

The project documents that MRN generation and appointment conflict checks are not fully concurrency-hardened. Database uniqueness constraints provide protection against certain duplicate outcomes, but they do not represent a complete concurrency strategy.

This limitation is important to record honestly. A database design can be structurally correct while still requiring additional work for high-concurrency production behavior.

## 4.9.10 Database testing considerations

Automated backend tests use EF Core InMemory. This is useful for fast isolated tests but does not reproduce every PostgreSQL behavior.

Consequently, database verification has two complementary levels:

1. automated application tests using an isolated provider;
2. manual end-to-end testing against PostgreSQL.

This distinction prevents test results from being interpreted more broadly than the test environment supports.

## 4.9.11 Engineering lesson

The main database lesson was that relational design is a model of business meaning, not merely a storage exercise. The separation of Patient, Appointment, and ClinicalVisit reflects different concepts in the workflow.

The database therefore became clearer once the domain analysis was complete.
