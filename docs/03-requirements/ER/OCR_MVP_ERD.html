Open Clinical Record — MVP Entity Relationship Model

Approved scope: Patient Management · Patient Chart · Appointment Management

Application roles: Receptionist / Front Desk · Nurse / Clinical Staff · Clinician / Doctor

Design boundary: The model is deliberately small enough for the remaining internship period. Diagnosis, treatment, prescriptions, medical reports, laboratory, pharmacy, billing, insurance, radiology, patient portal, FHIR/international-standard integration, advanced analytics, and enterprise scheduling are deferred.

1. Entities

PATIENT

  • PK patient_id
  • UQ patient_identifier
  • first_name, middle_name, last_name
  • date_of_birth, sex
  • phone, email, address
  • emergency_contact_name, emergency_contact_phone
  • status, date_of_death
  • created_at, updated_at

USER

  • PK user_id
  • UQ username
  • password_hash
  • first_name, last_name
  • role — Receptionist, Nurse, Clinician only
  • active, created_at, last_login_at

ALLERGY

  • PK allergy_id
  • FK patient_id
  • allergen, reaction, severity, status
  • recorded_at, recorded_by

MEDICATION_HISTORY

  • PK medication_history_id
  • FK patient_id
  • medication_name
  • dosage, frequency, route
  • status, start_date, end_date
  • notes, recorded_at, recorded_by

PATIENT_ALERT

  • PK alert_id
  • FK patient_id
  • alert_type, description, severity
  • active, created_at, created_by, resolved_at

APPOINTMENT

  • PK appointment_id
  • FK patient_id
  • FK clinician_id → USER
  • scheduled_start, scheduled_end
  • reason, status, notes
  • created_at, updated_at, created_by

APPOINTMENT_HISTORY_EVENT

  • PK event_id
  • FK appointment_id
  • event_type
  • previous_status, new_status
  • previous_scheduled_start, new_scheduled_start
  • event_time, actor_user_id, reason

VISIT

  • PK visit_id
  • FK patient_id
  • FK nullable appointment_id
  • visit_type, status
  • check_in_time, check_out_time
  • notes

AUDIT_EVENT

  • PK audit_event_id
  • FK user_id
  • action, entity_type, entity_id
  • occurred_at, details

4. MVP Validation

  • Exactly three business modules.
  • Exactly three application roles; no Administrator role.
  • A patient exists before an appointment references that patient.
  • A walk-in visit can exist with VISIT.appointment_id = NULL; no fake appointment is created.
  • Appointment history is preserved through APPOINTMENT_HISTORY_EVENT.
  • Medication history is explicitly separate from prescription management.
  • No diagnosis, treatment, prescription, report/document, lab, pharmacy, billing, insurance, radiology, portal, or FHIR entity is included.
  • Patient is the central record connecting chart and appointment/visit history.
  • The logical model is database-independent and suitable for React + ASP.NET Core + REST implementation.

5. Final Design Notes

The physical database should add appropriate data types, indexes, foreign-key constraints, uniqueness constraints, and transaction behavior. Backend authorization must enforce the role matrix independently of React UI visibility.

This ERD is the MVP logical data-model baseline. Optional concepts such as vital signs may be added only after explicit confirmation that they fit the remaining implementation time.
